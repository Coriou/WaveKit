# Receiver capabilities design

Status: read-only foundations and route composition implemented and software-validated in protected and legacy modes. Current numerical regional data and physical receiver support/readback remain unavailable or unknown. No browser, regulatory or hardware qualification is implied.

See [requirements](requirements.md), [design](design.md) and [tasks](tasks.md).

## Scope and authority

Provide a read-only pull projection of present source/session evidence. The first slice accepts only a valid current-session 12-byte RTL0 peer header as peer-advertised tunerType and gainCount. Physical support/readback, model identity, RF ranges, gain tables/presets and bias-T remain unknown. Current command values are unknown because existing tuner state lacks per-field current-session and origin evidence. A connected but stalled payload does not invalidate current-session metadata or prove receiver/sample health.

Existing SourceManager header/status getters can retain disconnected history or mutable caps and cannot establish coherent source/session identity. The new synchronous evidence accessor, bounded identity allocator and full callback/resource ownership corrections below are required integration dependencies. Existing header parsing/stripping and command behavior otherwise remain unchanged. No receiver-host probing, acquisition, tuning, command listeners, history cache or registry extraction belongs in this slice.

Core command validation describes admitted API argument policy, not receiver RF support. Write submission is not applied/readback acknowledgement. Relay observations, configured declarations, peer advertisement and physical readback stay separate. No current tuner placeholder is promoted into physical capability evidence.

## Closed DTO contract(future packages/api-types/src/receiver-capabilities.ts)

All objects additionalProperties:false, required fields explicitly listed; no arbitrary metadata maps, URLs, hosts, filenames, raw header buffers, exception/log messages or device serials. DTO consists of:

ReceiverCapabilities = {schemaVersion:1, sourceId:string, sourceIncarnation:string, sessionId:string|null, snapshotId:string, capturedAt:string, source:{type:'rtl_tcp'|'sdrpp-network'|'recording',kind:'iq'|'audio_pcm'|'recording',format:'U8_IQ'|'S16_IQ'|'S16LE'|'FLOAT32LE'|'auto'}, connection:'connecting'|'connected'|'disconnected'|'ended', delivery:{state:'disconnected'|'waiting'|'streaming'|'stale'|'paused'|'ended',lastSampleAt:string|null,sampleAgeMs:number|null,timeoutMs:number}, peerHeader:HeaderEvidence, controls:ControlEvidence[15], declaredStream:DeclaredStream}.

sourceId is exact configured ID subject to the unified representability predicate: UTF8 1..256 bytes AND decoded JavaScript string.length<=100 UTF16 code units, plus scalar/separator/control rules below; existing config has only min1, so IDs exceeding either bound or otherwise unrepresentable are not retroactively rejected/renamed: capability projection fails closed with RECEIVER_CAPABILITIES_LIMIT rather than truncating. Incarnation/session/snapshot IDs are fixed32 lowercasehex observation tokens, allocated by the exact bounded allocator below. Their numeric construction is not receiver/hardware identity; consumers must treat them as opaque and compare only within one running API instance. Deterministic nonreuse is guaranteed within one SourceManager lifetime, not across process restart. Internal source/attempt object identity remains callback authority. capturedAt/lastSampleAt are UTC ISO fixed24char timestamps; nonfinite/out-of-Date-range evidence fails projection. Ages nonnegative finite safe integers, saturated at Number.MAX_SAFE_INTEGER; source rate/frequency numbers finite positive safe integers, invalid configured values produce conflict. No physical freshness implied by timestamps.

HeaderEvidence is exact union:
{state:'advertised',provenance:'rtl-peer-header',sessionId:string,observedAt:string,tunerType:uint32,gainCount:uint32}
| {state:'unknown',reason:'not-connected'|'awaiting-header'|'partial-header'|'invalid-header'|'format-not-captured'}
| {state:'not-applicable',reason:'non-rtl-transport'|'non-iq-source'}.
No magic echoed. Valid requires exactly 12 bytes and literal first bytes [0x52,0x54,0x4c,0x30] (no ASCII decoding/high-bit masking); any uint32 tunerType/gainCount retained as numeric peer claims, including0/unknown/vendor values and hugecounts; never used for allocations/loops or lookup names. Partial byte count is private 0..11; no partial parsed claims. Invalid remains invalid for session; payload does not repair it. Existing parser/stream stripping need not change.

DeclaredStream={provenance:'source-config-or-core-metadata',sampleRateHz:number,centerFrequencyHz:number|null}; this is explicitly not measured/readback and cannot be called configured original tuning after commands modified caps. Original configured versus effective metadata is not conflated: initial slice provides only this labeled effective declaration, not a fabricated original baseline.

ControlEvidence={id:ControlId,unit:Unit,command:{state:'implemented',opcode:uint8,validation:{authority:'admitted-rest-argument-policy',rule:Validation}},transport:{state:'applicable'|'not-applicable',reason:'rtl-tcp'|'non-rtl-transport'},physical:{state:'unknown',reason:'no-qualified-readback'},currentValue:{state:'unknown',reason:'session-qualified-command-evidence-not-provided'}}.

Never label raw IF gain as dB without qualified evidence. This says routing protocol applies, not that a write now succeeds; connection separately states availability. Non-RTL physical unknown, NOT unsupported. Future physical supported/unsupported requires separately reviewed qualified provider and DTO version; v1 deliberately has no physical supported boolean.

Validation closed union: {kind:'integer-range',min:number,max:number} | {kind:'integer-ranges',ranges:[{min,max},{min,max}]} | {kind:'enum',values:string[]} | {kind:'boolean'} | {kind:'uint16-pair'}. These constants are representation of current API validation ONLY, explicitly not hardware RF/rate/gain limits. No presets/table or bias-T fact follows. One shared readonly descriptor is the authority for admitted REST argument policy: Integration exports TUNER_REST_COMMAND_POLICY from tuner-controller.ts, with numeric rules derived from existing VALIDATION/RTL_SAMPLE_RATE_RANGES, and enum/boolean rules used by existing tuner REST schemas. Typed enum/boolean setters themselves map/coerce values and are NOT claimed runtime validators. Integration makes the existing REST schema construction consume the descriptor without changing accepted inputs; numeric setter validation remains unchanged and implementation tests compare numeric acceptance, while route tests compare enum/boolean acceptance. Each controls array exactly 15 rows in opcode order; ranges at most2, enums at most3, strings enum only. One DTO maximum 16 KiB UTF8 JSON, enforced after detached projection serialization. Error maximum 256 bytes with fixed authored strings. Retained state: provider constant configuration only, no cache/history/listeners/timers; source accessor state adds constant tokens/timestamps/status and existing 12-byte capture per registered source, no retired map.

Configured/commanded/observed/readback separation is intentional: current TunerState may carry desired values across reconnect and cannot prove which field was written during this current session, nor distinguish per-field relay versus REST from its getter. v1 currentValue therefore UNKNOWN even when old tuner getter has a value. Existing /api/tuner remains independent command/configuration view with unknownFields and existing provenance limitations; do not embed its placeholders as current physical or commanded capability evidence. A future session-qualified command observation interface would need exact SourceManager session token captured at write/relay receipt and origin per field, new review/allocation. No such seam is needed for first slice and no command listeners are added here.

## Exact bounded allocator and reader results

A SourceManager owns one unsigned 128-bit BigInt next counter initialized to 1; zero reserved. allocate() checks 1<=next<=2^128-1, returns next.toString(16).padStart(32,'0'), increments next. All incarnation, session and snapshot tokens share this single namespace. Constant 129-bit counter state; no issued-token set, randomness, collision lookup or retired map. No collision is possible before exhaustion within this manager lifetime. Tokens may repeat after manager/process restart; cross-instance persistence/caching is unsupported, responses no-store. Allocator implementation failure (invalid counter/type/range) latches allocatorFailed for the remaining manager lifetime, same semantics as exhaustion. No fallback random/reused token. Injected duplicate/rollback allocator output in tests is an implementation invariant violation, not a production collision-handling alternative.

Registration tries one incarnation allocation before map publication; allocation failure records evidenceUnavailable on that source but NEVER rejects/aborts operational registration, socket creation or recording start. Each network attempt separately tries session allocation; incarnation failure is not repaired by later attempts. Session allocation failure makes that attempt evidenceUnavailable even if operation connects/streams. Recording needs no session allocation. Snapshot reads allocate once per get/page capture after selection and identity availability validation; snapshot failure returns unavailable without mutation of operational state. Exhaustion/allocator failure is permanent until a new SourceManager lifetime (new operational manager is NOT created by this feature). No reads/reconnects retry allocation to recover unavailable registration/attempt. Old allocated identities never substitute. Missing source is evaluated before allocator status; an empty page needs no snapshot allocation and returns empty successfully even after exhaustion. Subsequent new registrations/attempts remain operational but evidence-unavailable. These are explicit recovery rules, not implementation choices.

Internal reader contracts are synchronous closed results:
read(id): {kind:'missing'} | {kind:'unavailable'} | {kind:'conflict'} | {kind:'limit'} | {kind:'present',evidence:SourceReceiverEvidence}.
readPage(after,limit): {kind:'unavailable'|'conflict'|'limit'} | {kind:'candidates',candidates:readonly SourceReceiverEvidence[],capturedAt:number,snapshotId:string|null}. candidates.length is0..limit+1 (<=17); empty candidates snapshotIdnull; nonempty all share envelope snapshotId and capturedAt. Reader does NOT expose hasMore, discard lookahead or perform public DTO/descriptor projection.
Reader may throw only unexpected implementation failures; provider maps those to FAILED. get maps missing toNOT_FOUND, unavailable toUNAVAILABLE, conflict toCONFLICT, limit toLIMIT. list fails the WHOLE page for any selected or lookahead source unavailable/conflict/limit, never skips it. Reader validates only source-owned identity availability, primitive copy safety and representability, NOT public projection/schema/descriptor/bytes. After selection and those source checks, it samples ONE now and allocates ONE snapshot token BEFORE copying up to 17 candidate records. Failed source prechecks consume no snapshot token; empty page consumes none. Successful allocation consumes the token permanently even if copying subsequently conflicts/throws or provider projection/schema/serialization/descriptor validation rejects. Allocation failure returns unavailable with zero candidates; no allocation retry or second read. All copied candidates share now/token. Reader get uses identical ordering for one candidate, missing/precheck failure consumes no token; later provider failure consumes its successful token. Returned detached copies may be stale after this synchronous capture; projection never rechecks live source state. Provider disposed or absent =>UNAVAILABLE before reader call. All callbacks/writable APIs absent from reader interface.
